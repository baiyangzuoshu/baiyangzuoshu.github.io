&emsp;&emsp;最近，我把一款 Cocos Creator 2.4.15 飞机大战小游戏逐步接入自己的 FrameWork。迁移本身分成 00 到 09 共十个模块，最终都完成了验收。但这篇文章想重点记录的不是飞机大战怎么改，而是另一个更值得复用的问题：如何用 Skill 把一次迁移的经验，变成下一次可以直接调用、持续改进并能检查质量的工作流。

&emsp;&emsp;对我来说，Skill 不是项目结束后补写的说明书，而是迁移工作的主入口。它告诉协作者先看什么、按什么原则推进、哪些事情不能做、怎样验证结果；项目文档记录当前迁移计划和验收状态；评测案例则用来检查 Skill 有没有遗漏重要边界。飞机大战只是这套方法的第一个实战样本。

## 为什么迁移工作需要 Skill

&emsp;&emsp;迁移一个旧游戏，往往不是单纯改代码。需要理解 Creator 版本、旧项目入口、资源和 UUID、场景与 prefab 绑定、目标框架边界、运行时流程以及人工验收方式。若这些知识只留在聊天记录或个人记忆里，下一个项目就会重复踩坑；若全部写进一份巨大的迁移文档，又很难区分通用原则和某个项目的特殊事实。

&emsp;&emsp;Skill 的价值是把可重复的方法做成明确入口，并在真实项目里持续检验。它不是要预先规定每个项目长什么样，而是指导协作者先调查事实，再创建适合当前项目的计划与约束。

## Skill 如何分层

&emsp;&emsp;这次实践里，迁移知识分成几层，各自回答不同问题：

| 层次 | 回答的问题 | 在迁移工作中的职责 |
| --- | --- | --- |
| 通用迁移 Skill | “迁移项目时，通用上应该怎么做？” | 提供跨项目的调查顺序、迁移原则、执行节奏与验证方法 |
| 项目 Skill | “这个游戏有哪些已经确认的事实和特殊约束？” | 保存项目专属入口、资源、命名、模块边界和生命周期信息 |
| `AGENTS.md` | “在这个仓库里，协作者先读什么、遵守哪些全局规则？” | 做精简路由与仓库级约束，不重复整本手册 |
| `docs/migration/` | “当前项目要迁哪些模块，做到哪一步，如何验收？” | 保存总计划、模块步骤、依赖、状态及实际验收记录 |
| `.codex/skill-evals/` | “Skill 在不同情形下能否给出符合规则的指导？” | 用正例、反例和边界案例检查 Skill 的覆盖与一致性 |

&emsp;&emsp;这几层不能混为一谈。通用 Skill 不应写死飞机大战的 prefab 名称；项目 Skill 不应复制通用迁移流程；`AGENTS.md` 不应膨胀成所有业务细节的仓库百科；迁移文档里的“计划完成”也不能替代用户验收；Skill eval 更不能冒充游戏运行测试。

## 从调用通用 Skill 到建立项目 Skill

&emsp;&emsp;新项目开始时，先调用通用迁移 Skill，让工作从调查而不是猜测开始。通用 Skill 负责提醒协作者确认 Creator 版本、工程入口、旧项目语言、资源加载方式和框架边界；这些事实确认之后，再为目标游戏创建项目 Skill 和迁移文档。

&emsp;&emsp;飞机大战的源项目使用 Cocos Creator 2.4.15 和 JavaScript `cc.Class`，目标工程使用同一版本的 TypeScript 与 FrameWork。调查确认后，项目自己的约束包括：保留 `assets/old/` 作为可运行基线；把目标资源按 `BundleMain`、`Res`、`Scripts` 分工；采用单场景，由 `UIRoot → UIMain → UIGame` 组织界面；UI 优先走框架基类和 UIManager；迁移资源时维护新的 UUID 与映射关系。

&emsp;&emsp;这些结论分别落在适合的位置：通用迁移规则进入通用 Skill，飞机项目的资源和界面事实写入项目 Skill，仓库入口写入 `AGENTS.md`，模块步骤与验收证据写入 `docs/migration/`。因此第二个项目并非复制飞机项目的目录和 prefab，而是复用“先调查、再分层记录、最后分模块实施”的方法。

## Skill 如何随着项目迭代

&emsp;&emsp;好的 Skill 不靠一次性写得很长，而是随着真实执行不断修正。遇到问题时先判断它属于哪一层：如果是所有迁移项目都可能遇到的原则，就更新通用迁移 Skill；如果是当前游戏的结构或事实，就更新项目 Skill；如果是本次模块的具体路径和结果，就更新模块文档。

&emsp;&emsp;飞机大战迁移中，几次具体问题推动了规则迭代：

1. **旧项目必须继续可运行。** 迁移采取复制而非移动或删除，确保旧项目仍是对照基线；新项目只逐步接管已经验收的功能。
2. **目标 UI 要优先使用框架。** 页面使用框架 UI 基类和 UIManager，不另建平行的场景路由；单场景结构下，由 GUI prefab 承载界面流程。
3. **命名冲突不只看导出的类名。** Creator 2.4 quick compile 还可能受脚本文件 basename 影响，因此目标脚本需要独立文件名，并检查类名、`.meta` UUID 与 prefab 绑定。
4. **验收日志要能说明状态变化。** 例如界面打开、资源加载、对象回收、动画结束和退出清理要有可判断的证据；但日志仍需与静态引用检查及 Creator 预览配合，不能单靠日志证明画面正确。
5. **按切片验收，不提前宣称后续功能已接入。** 当前只迁移登录时，登录后尚无首页属于合理中间状态，不应为了“看起来完整”而接入未迁移的旧流程。

&emsp;&emsp;每次更新还要避免把一次性的故障排查步骤过拟合进通用 Skill。例如，飞机的三个 Hero prefab、五类敌机和具体 GUI 路径是项目事实；下一款游戏可能完全不同。通用 Skill 应记录如何调查与验证这些事实，项目 Skill 才记录实际结果。

## Skill eval：检查指导质量，而不是替游戏验收

&emsp;&emsp;Skill 写完或改完后，还需要问：它能否处理正常情况、明确拒绝违反原则的方案，也能否识别容易混淆的边界？因此评测案例不应只有正向范例，还应该包含反例和边界案例。

&emsp;&emsp;例如，评测可以检查协作者是否会建议删除 `old/`、把普通多页面项目拆成多个场景、绕过框架 UIManager、照搬上个游戏的资源路径，或把一条“加载成功”日志当作整个模块验收通过。若 Skill 对这些情况回答不稳定，就要补充或澄清规则，再用相应案例回归。

&emsp;&emsp;评测的对象是 Skill 的指导能力，不是 Cocos 项目的运行状态。它不能证明 prefab 绑定正确、按钮可点击、敌机确实生成，也不能替代 Creator 运行和用户验收。完整验证仍然分工明确：静态检查审资源与引用，运行日志证关键状态，Creator 预览检查视觉和交互，用户确认模块验收结果。

## 飞机大战：作为工作流的实战样本

&emsp;&emsp;在上述 Skill 工作流指导下，飞机大战迁移拆成 00—09 十个模块：先复制和验证 FrameWork，再建立目标入口、迁移资源、接菜单与选机，然后接局内玩家、敌机、暂停结算音频，最后审计旧脚本和资源引用。每个模块单独记录目标、依赖、测试方式和验收状态，当前模块通过后才继续下一模块。

&emsp;&emsp;这套节奏曾避免一个容易误判的问题：早期点击菜单后已经能玩，但实际进入的是 `assets/old/` 中的旧场景。表面上功能可用，迁移边界却没有建立。之后通过检查目标入口、GUI 路由和运行日志，才确认目标流程真正由新框架接管。

&emsp;&emsp;另一个例子是资源引用。资源复制到 `BundleMain` 或 `Res` 后，还需要为目标副本维护 UUID 映射，并检查 prefab 对 SpriteFrame 等依赖的引用。最后的静态审计确实发现了缺失引用。这个结果回馈给工作流的经验是：模块验收之外还需要收尾审计，且 Creator 视觉预览不能被静态检查取代。

&emsp;&emsp;到目前为止，飞机大战 00—09 模块均已验收，最近一次收尾修复提交为 `b8ab05d8`。这不是说下一个项目可以照抄同一份迁移步骤，而是说明通用 Skill、项目 Skill、迁移文档和评测各自承担的角色，在一个完整案例里得到了验证。

## 第二个项目如何复用这套 Skill

&emsp;&emsp;下次迁移时，我希望按下面的循环开展工作：

1. 先读取通用迁移 Skill，扫描源项目与目标框架，记录版本、入口、资源和运行现状。
2. 根据扫描结果建立项目 Skill、`AGENTS.md`、迁移总计划与逐模块文档，不预设新游戏与飞机大战相同。
3. 为项目 Skill 的关键约束准备正例、反例和边界 eval，检查指导是否清晰且没有把项目特例误当通用规则。
4. 先搭好框架入口，再按垂直切片迁移；每个切片提供可观察的验证证据并等用户验收。
5. 把执行中的新发现归还到正确层次：通用方法回通用 Skill，项目事实回项目 Skill，执行状态回迁移文档，指导缺口回 eval。

&emsp;&emsp;这样，Skill 才不只是“写过一次的文档”，而是贯穿项目调查、实施、验证和复盘的主线。飞机大战迁移的意义，在于为这套 Skill 工作流提供了第一组真实约束、失败案例和验收结果；第二个项目则会继续检验它，并推动它变得更可靠。
