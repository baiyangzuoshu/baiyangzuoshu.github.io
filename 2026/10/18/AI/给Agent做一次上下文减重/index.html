给 Agent 做一次上下文减重：从工具按需加载到历史压缩

  我在实际使用 Agent 时，发现 API 调用特别消耗 token。用 AI 分析后才发现，每轮请求都带上了不少无关历史、长日志和旧工具结果，却没有及时摘要、压缩或清理；工具定义也没有按任务筛选，不需要的工具同样发给模型。

  上下文越积越多，不仅浪费 token，也会淹没关键信息，增加模型判断偏差的风险。于是我开始给 Agent 做上下文治理：工具按需加载，大结果只保留预览和引用，旧历史分层归档，必要时再摘要。优化不是盲目删信息，而是让模型只看到当前任务真正需要的内容。

  这次改造的目标不是单纯把文本剪短，而是回答两个工程问题：每次请求的 token 花在哪里？在不丢掉当前任务所需信息的情况下，哪些内容可以不再重复发送？

模型为什么需要前文

  语言模型每次生成回答，都是根据当前输入计算接下来最合适的内容。它不会自动看到 Agent 程序里的文件、刚执行的搜索结果，或上一次 API 调用的完整对话。没有把这些信息提供给它，它就无法依据这些信息继续推理。

  例如，用户只说“帮我查构建为什么失败”。模型可以先决定搜索日志，但真正的错误原因要等搜索工具返回。Agent 拿到 Module not found: xxx 后，再调用模型分析。如果第二次请求只写“请给出修复方案”，模型既不知道原任务，也没看到报错内容，无法判断应该修复什么。

  如果模型继续调用 read_file，Agent 就会把必要的前文和新的文件内容带入第三次请求。随着工具轮次增加，消息历史可能不断变长；如果旧日志仍然留在历史里，后续请求就可能继续带上它。这就是本文所说的“重复携带上下文”：Agent 为了让模型能接着当前任务推理，在后续 API 调用中重新提供所需的历史和工具结果。

  这不是模型拥有永久记忆，也不是每个 Provider 都要求客户端逐字重发所有历史。有些 API 提供服务端会话状态，客户端可以传会话标识；有些支持 prompt caching。它们会改变历史如何传递或如何计费，但模型生成时仍要能访问相关信息。对本项目来说，Agent 会在每次请求中显式组装并发送系统提示、当前可用工具定义和消息历史；缓存可能降低重复前缀的计算费用，却不会自动把旧日志从任务上下文中压缩掉。

先量清楚，再谈节省

  优化前需要知道请求由什么组成。现在每次 Provider 请求都会分别统计系统提示、工具 schema、历史消息和工具结果的字符数或估算 token，并在请求完成后记录 Provider 能返回的输入、输出和缓存 token。记录只保留数量、耗时和原因，不保存完整提示正文；摘要、重试和子 Agent 请求也归到同一次任务的消耗里。

  这里必须区分两种数据。字符换算出来的是估算值，Provider 返回的 usage 才是这次请求的实际 token 数据；有些 Provider 不提供缓存或费用字段时，这些指标只能标成未知。没有真实 usage，就不能把估算结果写成账单节省。

第一笔开销：每轮都带着整套工具

  工具定义会随每个模型请求重复发送。工具数量多、参数 schema 长时，即使用户只问一个简单问题，输入里也可能有大量本轮用不到的定义。

  改造后把能力分组：文件、搜索等基础工具保持可见；研究、图片、调度、团队等能力先通过短目录发现，确定需要后才加载完整说明。工具仍通过原来的注册表执行，权限检查和参数校验不会因为“未展示”而跳过。顺序保持稳定，减少请求前缀的无意义变化，也有利于 Provider 的提示缓存。

  这解决的是固定开销。代价是模型可能需要先发现能力再加载工具，因此要观察新增的往返是否抵消了省下的 schema token。工具按需加载不是越激进越好，简单任务收益最大，复杂任务则应确保能力容易被发现。

第二笔开销：工具把大段结果塞回上下文

  Shell 日志、搜索结果和大文件内容常常比用户原始问题长得多。若完整结果保存在对话里，后续每一轮都会继续携带它。硬截断虽然能控制长度，却可能把真正需要的那几行也截掉。

  现在大结果先保存完整内容，模型上下文里放执行状态、大小、有限预览和可恢复引用；需要细节时，再通过分页读取工具按行或范围取回。文件读取也支持起始行与行数。这样大输出不会自动变成每轮的固定负担，同时模型仍然能查到被省略的部分。

  这项设计还要防止另一种反效果：如果预览太少，模型会频繁补读，额外增加 API 往返。需要用长日志任务观察补读次数，并保留读取上限、存储容量限制和工作区隔离，避免把省下的上下文成本变成无界的磁盘和读取成本。

第三笔开销：历史对话越跑越长

  多轮 Agent 运行会把用户请求、assistant 的工具调用和工具结果累积起来。简单按消息条数裁剪有两个问题：一条消息可能很大；如果只删掉工具调用或只删掉结果，对话结构就会不完整。

  因此，请求前先按实际体积计算预算，预算中包括消息、系统提示和工具 schema，并为模型输出留出空间和安全余量。超出预算后，按层次压缩：保留新工具结果的预览；把模型已经读过的旧结果改成引用；按完整工具交互归档更早的消息块；仍然不够时才生成历史摘要。当前用户请求和必要的近期消息会独立保留。

  摘要本身也会消耗 token，所以它是最后一道手段，而不是每轮都做。摘要固定保存当前目标、约束与决定、已完成工作、证据和待办；摘要调用有输入、输出和次数预算，并沿用取消信号。历史未变化时复用摘要检查点，避免重复总结同一段内容；历史或工作区变化后则使检查点失效。

控制边界和失败恢复

  预算统一后，还需要明确区分请求次数、token 消耗和金额。原有按请求次数扣减的 RunBudget.cost 保持兼容，但不能再把请求次数误称为 token 或费用。不同模型使用各自的上下文窗口配置；未知模型采用明确标注的保守估算。

  Provider 请求也增加可选输出上限，普通回答、摘要和提取任务采用不同额度。如果模型因上下文超限而拒绝请求，只做一次压缩恢复；取消和预算耗尽则直接终止。这样可以避免无休止地压缩和重试，也让任务边界更可预测。

怎样验证有没有真的变好

  固定任务集应覆盖短问答、多文件检索、长构建日志、多轮修改、长对话续接，以及取消和超限恢复。每个任务同时记录输入与输出 token、API 和摘要次数、补充读取次数、完成情况、约束保留情况、耗时、缓存命中和费用。Provider 没提供的数据标成未知，而不是推测。

  当前仓库已经用模拟 Provider 跑了这些流程，检查了工具调用与结果配对、长日志按页读取、取消不触发重试，以及摘要检查点复用等行为。这验证的是运行逻辑，不是真实模型的 token、费用或网络耗时。另有一组短请求对照估算：假设原请求携带全部 62 个工具定义和完整提示，约为 23,213 个估算输入 token；按需发送约 10 个工具和精简提示，约为 5,062 个，估算差约 78%。这只是特定假设下的 schema 与提示估算，不能当作真实 API 节省比例。

  真正的收益需要在相同模型、相同任务和相同完成标准下做前后对比。若工具按需加载多走了一次模型请求，或大结果导致很多补读，最终总消耗未必下降。优化的目标不是让单次请求看起来更小，而是在任务完成率和约束保留不下降的前提下，减少整次运行的总输入、输出与额外调用。

这次改造解决了什么

  整体上，改造针对四类浪费：每轮重复发送所有工具定义；大工具结果持续占用后续上下文；长历史无预算地增长；摘要、重试和缓存等消耗缺乏分项观测。工具按需加载降低固定开销，结果引用减少长输出重复注入，分层压缩控制历史增长，任务级遥测则让优化结果可以核对。

  Agent 的 token 优化最终是上下文管理问题。该保留的任务目标、最近决策和新证据要保留；不再需要重复出现的 schema、旧日志和远期消息，则应以目录、引用或摘要替代。只有把实际调用、质量和成本一起测量，才能知道这些替换究竟让整个任务变得更省，还是仅仅把消耗挪到了别处。
